CONCEPTO CENTRAL
----------------
No conservar simultaneamente animaciones ya consumidas.
Debe existir un unico ANIMATION BANK reutilizable.
Debe existir un unico sistema/slot de PORTADA reutilizable con recursos graficos
distintos. No se planifican PORTADA A/B/C como motores o bancos residentes separados.

ENGINE V2E / LVLLVL
-------------------
Contrato visual validado:
1. scheduler copia front -> back;
2. delta de screen se define contra Frame N-1;
3. BITMAP_DELTA fast path: bitmap byte $00 = skip 8 celdas;
4. terminar screen oculto;
5. screen swap;
6. actualizar Color RAM;
7. no usar N-2;
8. no apagar DEN para ocultar transicion.

Color HALITO:

BANK16 / LIMPIEZA PARA BANCO UNICO
----------------------------------
Objetivo:
dejar de buscar huecos por Resource y construir un banco reutilizable para cualquier
ANIMACION, recargado durante las pantallas de PORTADA.

BANK16A = PASS
- backup temporal charset Resource01 movido de $9000-$97FF a $E800-$EFFF.
- INTRO LEMMINGS, Resource01, PORTADA, Resource02, SID, scheduler y fade siguen PASS.
- $9000-$97FF queda liberado durante CARGA 1.

BANK16B = FAIL
- KrillLoad extra intentando cargar probe $8D00-$9FFF durante INTRO.
- queda detenido con luz del drive encendida.

BANK16C = FAIL
- mismo concepto, solo $8D00-$8FFF.
- tambien queda detenido con luz del drive encendida.
- se descarta que el fallo se deba solamente a cruzar $9000.

BANK16D = FAIL
- probe $8D00-$9FFF movido despues de StopIntroA().
- CPU JAM.
- no promover.

BANK16E = FAIL
- probe reducido $8D00-$8FFF despues de StopIntroA().
- CPU JAM / cuelgue.
- patron comun de B/C/D/E: agregado de un KrillLoad adicional.

BANK16F = PASS / ULTIMO PASS CONFIRMADO
- base BANK16A.
- SIN nuevo KrillLoad.
- SIN nueva entrada D64.
- despues de StopIntroA(), la CPU llena directamente $8D00-$8FFF.
- pipeline completo sigue funcionando.

CONCLUSION BANK16F
------------------
$8D00-$8FFF ES RAM reutilizable despues de la INTRO.
Los FAIL de B/C/D/E no prueban que el rango sea invalido.
La evidencia apunta al KrillLoad extra / secuencia de I/O en esa fase.

CANDIDATO DE BANCO UNIVERSAL
----------------------------
NO ES TODAVIA CONTRATO FINAL.

Candidato:
- ANIMATION BANK: $4400-$9FFF = 23.552 bytes.
- CHARSET STAGE / backup: $E800-$EFFF = 2.048 bytes.

Para promoverlo deben cumplirse:
1. BANK16G PASS.
2. Integrar la extension dentro de la carga/loadlist existente.
3. Evitar KrillLoad adicional si esa es la causa confirmada.
4. Probar primero HALITO -> HALITO.
5. Solo despues reintroducir ESCHER.

ESCHER
------
Los intentos antiguos mostraron que adaptar el motor directamente a ESCHER mezcla
demasiadas variables.

Lecciones:
- no crecer codigo dentro de zonas criticas del decoder/gateways;
- preload futuro debe ser pasivo: no modificar metadata viva de la escena actual;
- Sprite Engine usa $3F00-$3FFF;
- charset $3800-$3FFF comparte esa pagina;
- glyph IDs $E0-$FF pueden entrar en conflicto con sprites activos;
- resolver incompatibilidades mediante Tool/perfil/packer, no parches por nombre.

ESTRATEGIA PARA ESCHER
----------------------
1. Terminar contrato del banco unico.
2. Validarlo con HALITO -> HALITO.
3. Hacer que ESCHER cumpla el contrato del motor.
4. No cambiar scheduler, SID, fade o timing para acomodar el arte.
5. Probar pipeline completo.
